# Серверный рендер страницы

Обычно рут просит конфиг из хука — то есть уже после гидрации. В HTML, который
отдал сервер, страницы нет: там пустой контейнер и запасной скелет. Человеку это
стоит лишнего похода в сеть, поисковому роботу — всей страницы: он видит пустой
`div`, и индексировать ему нечего.

`PieServerPage` это меняет: он сам забирает конфиг до рендера и отдаёт его руту.
Дерево рисуется в том же проходе, HTML уходит с содержимым, клиент гидрируется
поверх готовой разметки. Хосту не нужно ни ходить за конфигом, ни прокидывать
его дальше.

```tsx
// app/prime/report/[slug]/page.tsx — СЕРВЕРНЫЙ компонент, без 'use client'
import { PieServerPage } from '@swarm.ing/pieui/ssr'

export default async function ReportPage({
    params,
}: {
    params: Promise<{ slug: string }>
}) {
    const { slug } = await params
    return (
        <PieServerPage
            config={{ apiServer: process.env.PIE_API_SERVER! }}
            pathname="/prime/report"
            search={new URLSearchParams({ slug }).toString()}
            revalidate={300}
        />
    )
}
```

Если конфиг нужен ещё для чего-то — метаданных, JSON-LD, карты сайта, — рядом
лежит голая `loadPieConfig` с тем же интерфейсом; `PieServerPage` вызывает
именно её.

Тот же конфиг годится и для метаданных — второй запрос не нужен:

```tsx
export async function generateMetadata({ params }) {
    const { slug } = await params
    const config = await loadPieConfig({ /* … то же самое … */ })
    const card = findCard(config, 'PrimeReportCard') // обход дерева на стороне хоста
    return {
        title: card?.archetype?.poeticTitle,
        openGraph: { images: [card?.archetype?.photoUrl] },
    }
}
```

## Почему отдельный вход `@swarm.ing/pieui/ssr`

Сборка помечает `dist/index.*` директивой `"use client"` — весь главный вход
клиентский, и функция, импортированная оттуда в серверный компонент, утянет за
собой клиентскую границу вместо того, чтобы выполниться на сервере. В `./ssr`
баннера нет. Сам рут `PieServerPage` импортирует по имени пакета, а не
относительным путём: иначе сборка инлайнила бы его код в серверный вход — уже
без директивы, — и Next счёл бы рут серверным, упав на первом же хуке.

## Мини-апп: гибрид через `clientRoot`

Конфиг мини-аппа зависит от `initData`, который существует только внутри
клиента Telegram или MAX. Серверного рендера мини-аппа не бывает: запрос от
имени пользователя на сервере собрать не из чего.

Но страницу, у которой есть осмысленная ГОСТЕВАЯ версия — публичный разбор по
ссылке, витрина, лендинг, — можно отдать серверно и там:

```tsx
<PieServerPage
    config={{ apiServer }}
    pathname="/prime/report"
    search={`slug=${slug}`}
    clientRoot="telegram"
/>
```

Сервер берёт конфиг как `web` — гостевой, одинаковый для всех, — и отдаёт
готовый HTML. На клиенте встаёт `PieTelegramRoot`, дожидается `initData` и
перезапрашивает конфиг уже от имени пользователя: появляются лайки, владение,
всё личное. Первый кадр от этого не страдает — он уже на экране.

Для `/chat` или `/profile` смысла нет: без `initData` бэкенду нечего отдать, и
гостевой ответ будет пустым.

Если `initialConfig` всё же передан в `PieTelegramRoot`, рут не станет ждать
`initData` и отрисует переданный конфиг — ждать нечего, страница уже на экране.

## Ошибки

`loadPieConfig` бросает на любом ответе не 2xx. Это намеренно: что показать —
404, пустую оболочку или упасть — решает страница. Молча вернуть `null` значило
бы отдать роботу пустую страницу с кодом 200, и она такой в индекс и попадёт.
